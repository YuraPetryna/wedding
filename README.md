# Весільний фото-дроп

Гість сканує QR-код на столі → відкриває сайт → обирає фото → вони опиняються
на Google Диску наречених **в оригінальній якості**, **без жодної авторизації**.

## Як це працює

```
  Телефон гостя                Vercel (наш код)              Google
  ─────────────                ────────────────              ──────
  обрав 8 фото
        │
        │  1. POST /api/upload-session
        │     (тільки імена, типи, розміри — байтів немає)
        ├──────────────────────────────►
        │                          refresh_token
        │                          ────────────────────────────►
        │                          ◄──── 8 resumable-сесій ─────
        │  ◄──── 8 upload URL ─────┤
        │
        │  2. PUT байтів НАПРЯМУ, минаючи наш сервер
        ├───────────────────────────────────────────────────────►
        │  ◄────────────── прогрес, 308, 200 ────────────────────
        │
        │  3. POST /api/guestbook (ім'я + побажання)
        ├──────────────────────────────►  Google Sheets ────────►
```

Три вимоги із завдання і як саме вони виконані:

**Оригінальна якість.** Файл не проходить через жодне перекодування. Браузер
бере `File` з `<input type="file">` і віддає ті самі байти в `PUT`-запит.
Ми не малюємо його на `<canvas>`, не стискаємо, не змінюємо розмір, не чіпаємо
EXIF. Наш сервер бачить лише ім'я, MIME-тип і розмір — байтів він не торкається
взагалі. Це водночас обходить ліміт тіла запиту Vercel у 4.5 МБ: інакше фото
з сучасного телефона просто не пролізло б.

**Без авторизації гостей.** Токен належить нареченим і живе тільки на сервері.
Гість отримує одноразовий upload URL на конкретний файл конкретного розміру —
і більше нічого. Ані токена, ані доступу до Диска в браузері немає.

**Стійкість до поганого зв'язку.** Файли понад 24 МБ ідуть чанками по 2 МБ;
якщо мережа впала, скрипт питає Google «скільки байтів ти вже отримав?» і
продовжує з цього місця, а не з нуля. На весіллі, де сто телефонів ділять
один Wi-Fi, це не теоретична проблема.

### Чому не Service Account

Поширена помилка. У сервісного акаунта **немає власної квоти Google Drive**:
файли, які він завантажує, належать йому й упираються в нуль байтів місця.
Обійти це можна лише через Shared Drive, а він доступний тільки в платному
Google Workspace. Тому тут — `refresh_token` звичайного Gmail-акаунта
наречених: працює безкоштовно, і фото одразу лежать у їхньому Диску.

### Чому scope саме `drive.file`

Застосунок просить рівно один дозвіл — `drive.file`, доступ **лише до тих
файлів, які створив сам**. Google класифікує його як **не чутливий**, і з цього
випливають дві дуже практичні речі:

* застосунок не треба відправляти на перевірку в Google;
* `refresh_token` **не протухає через 7 днів**, як це відбувається з чутливими
  scope у режимі Testing. Токен, виданий за місяць до весілля, доживе до нього.

Плата за це одна: папку й таблицю має створити сам застосунок, а не людина
руками в інтерфейсі Диска. Саме тому їх створює скрипт `npm run auth`.

## Крок 1. OAuth-клієнт у Google Cloud

Робіть це **під акаунтом наречених** — саме на цей Диск підуть фото.

1. Відкрийте [console.cloud.google.com](https://console.cloud.google.com/).
2. Вгорі зліва — селектор проєкту → **New Project**.
   Назва, наприклад, `Wedding Photos`. Створіть.
3. **APIs & Services → Library** → знайдіть **Google Drive API** → **Enable**.
   Там само увімкніть **Google Sheets API** (для книги побажань; якщо вона не
   потрібна — можна пропустити).
4. **APIs & Services → OAuth consent screen**:
   * User Type: **External** → Create;
   * App name: `Наше весілля`, ваш email у полях підтримки та розробника;
   * Scopes — нічого не додавайте, скрипт попросить сам;
   * Test users — теж пропустіть;
   * збережіть і поверніться на екран OAuth consent screen;
   * натисніть **PUBLISH APP** → підтвердіть. Статус має стати
     **In production**.

   > Це головний крок, який усі пропускають. У статусі *Testing* Google анулює
   > `refresh_token` через 7 днів, і сайт помре рівно напередодні весілля.
   > Оскільки ми просимо лише не чутливий scope, публікація відбувається
   > миттєво і **без перевірки Google**.

5. **APIs & Services → Credentials → Create Credentials → OAuth client ID**:
   * Application type: **Desktop app** (саме Desktop — тоді не треба
     реєструвати redirect URI вручну);
   * Name: `Setup script` → Create.
6. Скопіюйте **Client ID** і **Client secret** — вони знадобляться зараз.

## Крок 2. Один скрипт — і все налаштовано

```bash
npm install
npm run auth
```

Скрипт запитає Client ID, Client secret і назву папки, відкриє браузер,
попросить увійти акаунтом наречених — і далі зробить усе сам:

* забере `refresh_token`;
* створить папку для фото на Диску;
* створить усередині неї таблицю **«Книга побажань»** із заголовками;
* запропонує дописати всі змінні в `.env.local`.

На екрані попередження «Google hasn't verified this app» — це нормально:
натисніть **Advanced → Go to … (unsafe)**. Застосунок ваш власний і просить
доступ лише до файлів, які створить сам.

### Якщо наречені не поруч

Проєкт у Google Cloud може належати **вам** — важливо лише, чиїм акаунтом
підтвердять доступ. Тож наречені мають зробити рівно одну дію: увійти
і натиснути «Дозволити». Для цього є ручний режим:

```bash
npm run auth -- --manual
```

Скрипт не відкриває браузер, а друкує посилання — надішліть його нареченим.
Вони увійдуть, дозволять доступ і впруться в помилку «Не вдається відкрити
сайт»: Google перекидає на `localhost`, якого на їхньому комп'ютері немає.
Це очікувано — код авторизації вже лежить у рядку адреси. Нехай скопіюють
усю адресу й надішлють вам, а ви вставите її в скрипт. Далі все як звичайно.

Готова інструкція для них, без жодного технічного жаргону, лежить у
[ІНСТРУКЦІЯ-ДЛЯ-МОЛОДЯТ.md](ІНСТРУКЦІЯ-ДЛЯ-МОЛОДЯТ.md) — просто перешліть
цей файл.

### Якщо наречені тільки з телефоном

Спосіб вище там не працює. Мобільні браузери на редіректі в `localhost`
або впираються в помилку, або взагалі нікуди не переходять — а дістати
код із рядка адреси пальцем нереально.

Рішення: перекидати не на `localhost`, а на сторінку самого сайту, яка
нормально відкривається будь-де і має кнопку «Скопіювати код».

**1. Спершу задеплойте сайт** (Крок 4 нижче). Він чудово збирається ще
без Google-змінних — просто завантаження фото поки не працюватиме.

**2. Створіть ДРУГИЙ OAuth-клієнт**, типу **Web application**
(Desktop app приймає лише `localhost`, тому потрібен саме Web):

* **Clients → Create client → Application type: Web application**
* **Authorized redirect URIs → Add URI**:
  `https://ваш-проєкт.vercel.app/oauth/callback`
* Скопіюйте новий Client ID і Client secret

> URI має збігатися символ у символ, разом зі схемою `https://`
> і без слеша в кінці. Google звіряє його точно.

**3. Запустіть скрипт із цим редіректом:**

```bash
npm run auth -- --redirect https://ваш-проєкт.vercel.app/oauth/callback
```

`--redirect` автоматично вмикає ручний режим. Наречені відкривають
посилання, тиснуть «Дозволити» і потрапляють на
[/oauth/callback](src/app/oauth/callback/page.tsx) — сторінку з кнопкою
«Скопіювати код». Далі надсилають вам те, що скопіювали, а ви вставляєте
у скрипт.

Сама сторінка нічого не зберігає й не логує: код одноразовий, живе близько
десяти хвилин, а обміняти його на токен без `client_secret` неможливо —
а секрет лишається тільки у вас.

> Перед тим як надсилати посилання, **опублікуйте застосунок** (Крок 1.4).
> Інакше акаунт наречених доведеться додавати в Test users вручну, а токен
> протухне через 7 днів.

Результат виглядатиме так:

```
GOOGLE_CLIENT_ID=1234...apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=GOCSPX-...
GOOGLE_REFRESH_TOKEN=1//0c...
DRIVE_FOLDER_ID=1AbC...
GUESTBOOK_SHEET_ID=1XyZ...
```

> `GOOGLE_REFRESH_TOKEN` — це фактично ключ від Диска. Не комітьте його,
> не надсилайте в месенджери. `.env.local` уже в `.gitignore`.

## Крок 3. Запуск локально

Відкрийте `.env.local` і допишіть публічні змінні (див. `.env.example`):

```env
NEXT_PUBLIC_BRIDE=Олена
NEXT_PUBLIC_GROOM=Андрій
NEXT_PUBLIC_WEDDING_DATE=2026-09-12
NEXT_PUBLIC_HASHTAG=#ОленаІАндрій2026
```

Потім:

```bash
npm run dev
```

Відкрийте <http://localhost:3000>, завантажте пару фото і переконайтеся, що
вони з'явилися в папці на Диску — у повному розмірі, з тим самим EXIF.

**Перевірте якість чесно:** завантажте фото, скачайте його з Диска назад і
порівняйте розмір у байтах з оригіналом. Вони мають збігтися до байта.

## Крок 4. Безкоштовний деплой на Vercel

Безкоштовного тарифу Vercel Hobby вистачає для весілля з великим запасом.

### 4.1. Код у GitHub

```bash
git init
git add .
git commit -m "Весільний фото-дроп"
git branch -M main
git remote add origin https://github.com/ВАШ_НІК/wedding-photos.git
git push -u origin main
```

Переконайтеся, що `.env.local` **не** потрапив у коміт:
`git status --ignored | grep env`.

### 4.2. Імпорт у Vercel

1. [vercel.com](https://vercel.com) → увійдіть через GitHub.
2. **Add New → Project** → оберіть репозиторій → **Import**.
3. Framework Vercel визначить сам (Next.js). Нічого не змінюйте.
4. Розгорніть **Environment Variables** і додайте кожну змінну з `.env.local`
   (кнопка *Paste .env* приймає весь блок одразу). Не забудьте
   `NEXT_PUBLIC_*` — без них на сайті будуть імена за замовчуванням.
5. **Deploy**. Через хвилину-дві отримаєте адресу
   `https://ваш-проєкт.vercel.app`.

### 4.3. Закріпіть адресу

Додайте змінну `NEXT_PUBLIC_SITE_URL` з отриманою адресою і зробіть
**Redeploy** — вона потрібна для QR-коду й для прев'ю в месенджерах.

За бажанням: **Settings → Domains** → підключіть свій домен
(наприклад, `olena-andriy.com`). Або просто перейменуйте проєкт, щоб адреса
була коротшою — її ж друкувати на картках.

### 4.4. Перевірка на телефоні

Відкрийте сайт саме з телефона, по мобільному інтернету (не по домашньому
Wi-Fi), і завантажте фото. Це найважливіший тест: перевіряються і камера,
і HEIC з iPhone, і поведінка при слабкому сигналі.

## Крок 5. QR-коди на столи

```bash
npm run qr -- https://ваш-проєкт.vercel.app
```

З'явиться три файли:

| Файл | Для чого |
|---|---|
| `public/table-card.html` | Готова картка A6 — відкрити в браузері і `Ctrl+P` |
| `public/qr.svg` | Векторний код — віддати дизайнеру поліграфії |
| `public/qr.png` | Растр 1200 px — кинути в чат гостей |

Код друкується з рівнем корекції помилок **H (30%)**: працюватиме, навіть якщо
картку заллють шампанським або вона трохи зімнеться.

**Практичне про друк:** не робіть код меншим за 3 см — старі телефони
не впораються. Ставте картку так, щоб на неї не падав відблиск від свічок.
І покладіть по одній на кожні 4 місця, а не одну на стіл.

## Фотографії пари

Сайт тримається на фотографії — без неї це просто гарна типографіка.
Знімки беруться з теки `public/photos`, **нічого прописувати не треба**:
теку читає сервер, порядок задається іменем файлу.

| Файл | Куди піде | Яка потрібна |
|---|---|---|
| `01-...` | Фон першого екрана | Горизонтальна, з місцем під текст у центрі |
| `02-...` | Головний портрет в арці | Вертикальна |
| `03-...`, `04-...` | Два кадри в колажі | Будь-які, обріжуться в квадрат |

Чотирьох знімків достатньо. Розмір — 2000–3000 px по довшій стороні:
Next.js сам наріже адаптивні версії під кожен екран.

**Зараз там лежать тимчасові фони** — м'який розфокус «золотої години»,
згенерований `npm run placeholders`. Це не спроба вдати фотографію, а
свідомо абстрактне світло, щоб сайт не виглядав порожнім до того, як
з'являться справжні кадри. Коли вони будуть:

```bash
# 1. покладіть свої файли в public/photos з іменами 01-, 02-, 03-, 04-
# 2. приберіть тимчасові
npm run placeholders -- --clean
```

Якщо теку залишити зовсім порожньою, сайт не зламається: замість фото
малюється ботанічна графіка, і композиція лишається цілою.

> Ці фото — вітрина сайту. Вони **не** мають стосунку до знімків, які
> надсилатимуть гості: ті йдуть одразу на Google Диск і на сайті не
> показуються взагалі.

## Змінити тексти й кольори

**Імена, дата, хештег** — через `NEXT_PUBLIC_*` або напряму в
[`src/config/wedding.ts`](src/config/wedding.ts).

**Кольори палітри** — [`tailwind.config.ts`](tailwind.config.ts), блок `colors`.
Змінюєте `blush` / `sage` / `gold` — і весь сайт разом із анімаціями
перефарбовується.

**Шрифти** — [`src/app/layout.tsx`](src/app/layout.tsx). Зараз
Cormorant Garamond для заголовків і Manrope для тексту, обидва з кирилицею.

**Тексти на сторінці** — [`src/components/Hero.tsx`](src/components/Hero.tsx),
[`src/components/UploadFlow.tsx`](src/components/UploadFlow.tsx),
[`src/components/SuccessOverlay.tsx`](src/components/SuccessOverlay.tsx).

**Анімації** — усі криві, затримки й пружини зібрані в одному місці:
[`src/components/motion.ts`](src/components/motion.ts). Хочете зробити появу
повільнішою — правите `easeSoft` і `fadeUp`, і це застосується скрізь.

## Альтернативний бекенд: Google Apps Script

У теці [`apps-script/`](apps-script/Code.gs) лежить повністю робочий
запасний варіант — на випадок, якщо не хочеться мати справи з OAuth і Vercel.

Скажу чесно: **він гірший**, і ось чому.

| | Next.js + resumable (основний) | Apps Script |
|---|---|---|
| Розмір файлу | до 512 МБ і більше | ~35 МБ (base64 роздуває на 33%) |
| Відео з телефона | так | здебільшого ні |
| Докачка після обриву | так | ні, файл з нуля |
| Прогрес завантаження | точний, з подій XHR | тільки «йде запит» |
| Денні квоти | практично немає | скромні, на 100 гостей може не вистачити |
| Оригінальна якість | так | так |

Якість фото в обох варіантах однакова — Apps Script програє в надійності,
а не в якості. Інструкція з розгортання — у коментарях на початку файлу.

## Питання, що виникають

**Фото точно не стискаються?**
Точно. Стиснення могло б статися лише там, де зображення декодується — а ми
його не декодуємо ніде. Перевірити просто: порівняйте розмір у байтах до і
після. Google Диск, на відміну від Google Фото, зберігає файли як є і не має
режиму «економія місця».

**Скільки місця треба?**
Безкоштовно Google дає 15 ГБ на акаунт (спільно з Gmail і Google Фото).
Орієнтир: фото з сучасного смартфона — 3–8 МБ, тобто ~2000–4000 знімків.
Хвилинне відео 4K — близько 350 МБ, і ось воно з'їдає місце швидко.
Якщо чекаєте багато відео — на місяць весілля варто взяти Google One на 100 ГБ
(близько 2 $), а потім скасувати.

**Гість завантажив і закрив сторінку — фото збереглося?**
Так, якщо він побачив екран подяки. Під час завантаження браузер попереджає
про закриття вкладки.

**HEIC з iPhone не показує прев'ю.**
Так, деякі браузери не вміють показувати HEIC. На картці буде іконка з
підписом `HEIC` замість мініатюри — але **на Диск файл піде в оригіналі**.
Це суто косметичне обмеження браузера.

**Помилка «Google відхилив refresh_token».**
Найчастіша причина — застосунок лишився в статусі *Testing* (див. Крок 1.4)
і токен протух через 7 днів. Опублікуйте застосунок і виконайте
`npm run auth` ще раз, оновивши `GOOGLE_REFRESH_TOKEN` у Vercel.

**Помилка 404 при створенні сесії.**
`DRIVE_FOLDER_ID` вказує на папку, яку створили руками, а не скриптом. Зі
scope `drive.file` застосунок такої папки не бачить. Рішення: використайте ID
папки, яку створив `npm run auth`.

**Хтось може завантажити щось стороннє?**
Сервер приймає лише `image/*` і `video/*`, обмежує розмір і має простий
rate limit. Адреса сайту не індексується (`robots: noindex`) і відома лише
тим, хто був на святі. Для весілля цього достатньо; банківського рівня
захисту тут свідомо немає.

**Як потім розібрати фото?**
Якщо `CREATE_GUEST_SUBFOLDERS=true`, кожен гість отримує свою підпапку.
Плюс кожен файл названо у форматі
`2026-09-12_214305_Оля-Петренко_IMG_0042.jpg`, а ім'я та побажання
продубльовані в описі файлу і в `appProperties`. Навіть якщо таблиця з
побажаннями загубиться, дані лишаться при фото.

## Чекліст напередодні весілля

- [ ] У `public/photos` лежать справжні фото пари, тимчасові прибрані
- [ ] Застосунок у Google Cloud має статус **In production** (не Testing)
- [ ] Завантажив тестове фото з **iPhone** і з **Android**
- [ ] Завантажив тестове **відео**
- [ ] Порівняв розмір оригіналу й файлу з Диска — байт у байт
- [ ] Перевірив на **мобільному інтернеті**, не тільки на Wi-Fi
- [ ] На Диску наречених достатньо вільного місця
- [ ] QR-код надруковано, перевірено камерою з відстані 40 см
- [ ] `NEXT_PUBLIC_SITE_URL` у Vercel збігається з адресою в QR-коді
- [ ] Хтось із гостей-«тестувальників» пройшов шлях повністю, не питаючи вас
- [ ] Тамада знає, що нагадати гостям про QR-код
